Stockage haute disponibilité (DFS-N / DFS-R)

Supprimer le point de défaillance unique d'un serveur de fichiers en répliquant les données entre deux serveurs, avec un accès transparent pour les utilisateurs.

Période Jan – Mar 2026Rôle Seul
  • Windows Server 2025
  • DFS-N
  • DFS-R
  • GPO
  • pfSense
  • Proxmox
  • TrueNAS
Contexte

Dans une entreprise fictive (Innov Tech), un seul serveur de fichiers portait tout le stockage : en cas de panne, plus d'accès aux données. L'objectif était de rendre le service résilient sans changer les habitudes des utilisateurs.

Résultat

Les utilisateurs accèdent à un lecteur réseau unique (Z:). Si FS-01 tombe, FS-02 prend le relais automatiquement ; les données sont répliquées, versionnées (clichés instantanés) et sauvegardées sur TrueNAS. Validé par un cahier de recette.

Étapes de réalisation
  1. Architecture. Virtualisation sous Proxmox : contrôleur de domaine, deux serveurs de fichiers FS-01 et FS-02 (Windows Server 2025), pare-feu pfSense segmentant LAN Serveurs, LAN Clients et DMZ.
  2. Espace de noms DFS-N. Un chemin logique unique vers les partages, indépendant du serveur qui héberge réellement les données.
  3. Réplication DFS-R. Synchronisation des dossiers entre FS-01 et FS-02 pour que chaque serveur dispose d'une copie à jour.
  4. Droits et mappage. Modèle AGDLP (comptes → groupes globaux → groupes locaux de domaine → permissions) et GPO qui mappe le lecteur Z: selon le groupe.
  5. Sauvegarde. Clichés instantanés pour restaurer une version précédente, et sauvegarde sur TrueNAS.
  6. Recette. Cahier de recette : bascule en cas de panne, réplication, droits d'accès, restauration.

Difficultés rencontrées

  • Bien comprendre l'articulation DFS-N / DFS-R, et le moment où l'ordre de réplication importe.
  • Appliquer AGDLP sans multiplier les groupes inutiles.
